# YT6801 驱动踩坑笔记

> 从代码注释里迁出的实战经验。代码注释只写"做什么"，这里记录"为什么"和"怎么踩的"。
> 与代码版本对应：fork 自 yt6801-wired 1.4.22。

## 1. 寄存器与总线

- **MAC 寄存器全部相对 BAR0+0x2000**。漏加这个偏移的症状：MAC_VR 读成 0xfee00000、MDIO 永远 busy、MAC 地址读成 01:00:00:00:01:00。MGMT 块（PHY 复位 0x1004、WOL 0x1010、EFUSE 0x1500 区）不加偏移，直接相对 BAR0。
- **PCIDriverKit 的 MemoryRead32/Write32 返回 void**，出错时读到全 1（0xFFFFFFFF）。所以寄存器读写永远"成功"，MDIO 读到全 1 会让 busy 位永远置位、靠超时退出——这是设计上的兜底，不是 bug。
- **芯片级复位（SYS_RESET_REG 0x152c bit31，自清）会**：①重载 EFUSE 补丁表（每板 PHY 模拟校准，不做这步真线接收是死的）；②拉起 PHY 复位线（0x1004 变 0x16），要再释放；③清掉 BAR0 0x1000~0x1300 的 non-stick 寄存器（先存后恢复）；PCI 配置空间不受影响。
- **PHY 复位线（0x1004）保持复位时，MDIO 仍应答，但 PHY 不输出 MII 时钟**——DMA 停滞、线上无帧，症状极具欺骗性。释放序列：写 0 → 1.5ms → 写 1。
- **PHY 软复位会擦掉全部扩展寄存器**（AFE 五步配置），任何软复位后都要重写。回环自检有两次软复位，自检后必须重新配。
- **SPEC_STATUS 位布局**：bit10 link、bit13 duplex、bit14:15 速率（0=10M/1=100M/2=1000M）。reg.h 里 FXGMAC_EPHY_SPEED_MODE_BIT 11 是 MGMT_EPHY_CTRL 的口径，套过来会把百兆读成千兆。

## 2. MAC 地址

- 三级来源：EFUSE 补丁表（行 18 起，id 0x1520/0x1524 对应 MACA0LR/HR）→ MACA0 寄存器（BIOS 可能写过）→ 保底本地管理地址 02:59:54:36:80:01。全 0/全 FF/多播位一律判无效落下一级。
- **最终地址必须写回 MAC 地址过滤 0（MACA0LR/HR）**——硬件寄存器里残留的非法值会让 MAC 丢弃所有入帧，表现为"RX 永远没包"。
- EFUSE 行读协议：CTRL_0 写行号+START+ROW_READ，轮询 CTRL_1 DONE（最多 1000 次，每次 20-50µs），数据在 CTRL_1 bit31:24。

## 3. 描述符与 DMA

- **描述符必须指向驱动自建的 IODMACommand 缓冲，不能指向池包的 IOVA**。硬件不会把帧写进池包地址——描述符回写和 PL 长度看起来全正常，唯独缓冲区内容是旧数据（TX 侧同样成立：计数正常但发出的载荷是错的）。这是 1.0.72 时代最坑的一条，收发两个方向都要 memcpy。
- **池必须同时带 PoolFlagMapToDext 和 PoolFlagToDevice**：少 Dext 则 CPU 拿到池内偏移没法解引用；少 Device 则描述符拿到池偏移，OWN 照样回写、计数正常，但 DMA 读写的地址是野的，帧永远出不去。
- **dmaSpecification.maxAddressBits 必须 64**：描述符把 64 位地址拆在 desc0/desc1，限到 32 会把 IOVA 压到 4G 以下，映射硬件不工作。
- **描述符环必须物理连续**（PrepareForDMA 单段），硬件按序遍历，多段会算错下一描述符地址。
- **RDES2 的 B1L 必须等于缓冲大小**——RCR.RBSZ 不能替代它；B1L 不对时描述符照样完成但硬件不搬数据。
- **desc3 的 FL（总帧长）必须写**：desc2 的 B1L 只管 DMA 搬多少进 FIFO，FL=0 会被当零长帧，描述符永远不被取走。
- **TX 长度上限 = mtu + 14 + 4**：栈可能投递聚合出的大包（>1514），单描述符发出去对端会丢。
- **OWN 永远最后写**，且写前 OSSynchronizeIO()（拷贝必须先落内存）。

## 4. RX 环

- **满/空判据用显式 rxPending 计数，不能用 rxArm == rxClean**：整环挂满时 rxArm 回绕为 0，与 rxClean 相等，指针相等判据会读成"空环"。
- **环最多挂 RING-2 个，必须留一个空槽**：RX 尾指针回绕到环基址时，DWC 认为环空，一个描述符都不取。
- **RX 尾指针不能在通道启动前推**：启动 RX 会把 CARDR/RDTR 复位到环首，CARDR==RDTR 就是"环空"。SR 置位之后再推。
- **0 号槽必须有包**：自检后游标对齐到 1 号，但通道重启后 CARDR 回 0，挂包前强制 rxArm=0。
- **环基址必须在通道停着时写，再置 ST/SR 启动**。先启动再写基址 = DMA 按 TDLR=0 取描述符 → OWN 读成 0 → 挂起在 TU。顺带：停态写 TDLR 无效是误判，实际有效。
- **幽灵帧**：OWN 回写、PL 填好、但数据没动（缓冲里是旧内容）。交给栈会污染 ARP/ND 表，必须丢弃。EtherType=0 也是脏缓冲特征。
- **丢包判据看 MMC 硬件计数**（0x0780 RX 帧数、0x0794 CRC 错）：MMC 涨且 CRC=0 说明线路干净，丢包在驱动或上游；MMC=0 连 CRC 错都没有说明帧根本没进 MAC。

## 5. TX 环

- **TX 完成判据两条，任一满足**：①描述符 OWN 被清（标准做法，但这颗 IP 的 OWN 回写不可靠）；②CATDR 推过了它（安全，说明数据已进 MTL FIFO），留 4 个描述符余量。
- **环满不能直接放弃**：无中断环境下没有 TX 完成中断，栈配额耗尽后门铃停响就是死锁。用有界自旋（reclaim 边收边等，上限 2ms）。
- **TX 包立即归还**：数据已拷进驱动槽缓冲，等 DMA 完成再还在无中断机器上会死锁；立即归还保持栈发送配额，槽复用由 reclaimTx 按 CATDR 决定。
- 排查 TX/RX 卡死先看 CATDR/CARDR：指针不动 = DMA 没跑，别先翻描述符内容。

## 6. 中断与收包节奏

- **本机 MSI-X 不可用**（ConfigureInterrupts 成功但 irqCount 恒 0），PacketPoller 队列绑定也被拒（0xe00002c7）。最终方案：IOTimerDispatchSource 5ms 周期收割——注意早先"定时器会崩进程"的结论是错的，正确用法（OSAction + WakeAtTime 重排）很稳定。
- 收包延迟曾恒等于 ping 发包间隔：回包收割靠下一个 TX 门铃顺带完成，最后一个包永远没人收（表现为"ping 必丢一个"，实际线上无丢帧）。定时器方案解决，RTT 1s → 几十 ms。
- **DriverKit MMIO 比 Linux 快**，PHY MDIO 事务需要几十微秒，轮询必须显式 IODelay(10)×多次，否则等于没等。

## 7. 链路与自协商

- **先判链路再做 PHY 操作**：回环自检的软复位会拆掉已建立的链路。Start 流程：先 yt_wait_link → 有线跳过自检 → 无线才进回环。
- **卡上电后 PHY 在后台一直自协商**，插线 1-2s 起链，冷上电可能要 15s+（1.4.14 起等待窗口 30s）。
- **MAC 速率不能写死 1000M**：yt_sync_mac_speed 按协商结果配 MAC_CR 的 PS/FES/DM（1000M=PS0/FES0，100M=PS1/FES1），否则百兆口 link 灯亮但收发全废。
- **ANLPAR/STAT1000 要在链路起来后重读**：复位后 1 秒内读到的 LPA 恒为 0，不代表对端沉默。
- MDIO bit15 自清：BMCR 写 0x8140 后回读 0x0140 是正常的。

## 8. 系统栈（macOS 侧）

- **本版栈从不来拉 getSupportedMediaArray**（60 分钟零调用），媒体表必须注册成功后主动 ReportAvailableMediaTypes 推送，否则 ifconfig 报 SIOCGIFXMEDIA Input/output error。
- **Start 里过早 reportLink 会被丢**（ifnet 未挂完，active media 显示 none）。借栈必回调的 SetInterfaceEnable（ifconfig up/down 触发）补报即可。
- **四个队列都要显式 setEnable**，少一个栈就不投递。
- **IOVA 真相**：栈给的 IOUserNetworkPacket IOVA 硬件读写到的不是栈那份数据（自环同帧 28µs 往返：发 342 字节 EtherType 0x0800，绕回来 EtherType 0x756c，载荷是别的进程内存）。唯一解：自建缓冲 + memcpy，收发都是。
- 睡眠实测（1.4.22）：S3 正常，驱动睡醒存活，en5 IP 保留、链路自动恢复。阻睡元凶是 caffeinate 的 PreventSystemSleep 断言（连手动睡眠都拦）；ToDesk/coreaudiod 只挡闲置睡眠，不挡手动。
